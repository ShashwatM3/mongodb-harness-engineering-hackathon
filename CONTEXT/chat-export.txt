  The core concept is the strongest idea you've had so far. The reason is the
  narrative arc — it's a complete, understandable story that anyone in the room
  can follow: human does task on CCTV → robot attempts same task and scores
  35-55% across zones → robot watches human footage, analyzes its own failures,
  rewrites its brain → scores climb → ElevenLabs calls the Robotics Lead to
  report and ask for preferences → next iteration bakes those in too. That is a
  closed loop with a human-in-the-loop moment that is audible and physical in
  the room. It directly echoes what made Respondo a finalist, except here the
  phone call has a reason that's structurally core to the product rather than a
  feature bolted on.

  Against the judging criteria specifically:

  - Technical Demo (35%): This scores high because you have three distinct
    visual moments: zone performance percentages climbing on screen, the MongoDB
    brain/graph updating live in Atlas UI, and the ElevenLabs phone call. Three
    sensory hooks in one demo is rare. The risk: "the robot doing tasks" needs
    to be concrete on screen. If it's a simulation or an agentic software system
    with measurable outputs (not a physical robot), that's fine — but you need
    to decide this now and build it that way from the start. Don't plan for
    hardware and pivot to software at 2 PM.
  - Implementation Difficulty (30%): The CCTV video analysis piece is what
    elevates this above "a few AI prompts." Analyzing video frames with a vision
    model (Claude Vision or GPT-4V), extracting task steps, and feeding those
    into the brain-update loop is genuinely non-trivial and hard to recreate.
    The knowledge graph in MongoDB that represents the agent's evolving brain —
    zones, tasks, rules, performance snapshots, tool access policies — adds
    architectural depth. This is not a RAG wrapper. It is legitimately complex.
  - Impact Potential (20%): Warehouse robot onboarding is a real, documented
    pain point. Deploying a new robot into a warehouse currently costs
    $20,000–$50,000 in integration and tuning time, takes weeks, and breaks when
    the environment changes even slightly. An agent that self-onboards by
    watching humans is a commercially legible idea that any judge from
    enterprise software can immediately understand and value.
  - Creativity (15%): Using CCTV footage of humans as the "teacher" for the
    agent's rules — not for training model weights but for updating its
    scaffolding, guardrails, and tool access — is something that hasn't appeared
    in previous Cerebral Valley hackathon winners. Co-Dreamer used a knowledge
    graph + RL loop. ARANO used multi-agent simulation validation. Neither used
    human video observation as the recursive improvement signal. This is
    genuinely novel.

  Sponsor integration, honestly:

  - MongoDB Atlas + Agent Engine: Load-bearing and obvious. The hierarchical
    knowledge graph IS the brain — zones → tasks → rules → tool policies →
    performance history. MongoDB's document model handles this natively without
    needing a graph database. The Atlas UI showing the brain updating in real
    time during the demo proves deep integration. MongoDBSaver LangGraph
    checkpointer snapshots the brain state at each zone completion. Remove
    MongoDB and the brain has no persistent structure. Strong.
  - Raindrop RSI ($3,000 additive): This is the cleanest RSI alignment of any
    idea you've brainstormed. The agent literally updates its rules, context
    policies, guardrails, and tool access after observing its own performance
    and human footage. That is the definition of recursive self-improvement of
    the harness. You should win this prize if you execute.
  - ElevenLabs: The Robotics Lead call is perfect here. It's not decorative —
    it's a genuine human-in-the-loop feedback injection. Agent calls, reports
    zone scores, says "I've identified that I'm underperforming in Zone 3 on
    item sorting — do you have any operational preferences I should factor in?"
    The human responds, that preference gets stored in MongoDB and folded into
    the next iteration. This is a load-bearing architectural step, not a voice
    layer slapped on top.
  - Harness: You correctly identified this is the unclear one. Here is the
    answer: the robot's agentic behavior at any point in time is expressed as a
    Harness Worker Agent definition — its instructions, tool access, guardrails
    are all in that YAML. When the self-improvement loop decides to update the
    brain, it literally rewrites the Harness Worker Agent YAML and re-executes
    it. This makes the recursive part of "Recursive Harnessing" tangible and
    on-brand: the system is rewriting a Harness Worker Agent's own config.
    Remove Harness and there's no executable agent definition being evolved.
    That is load-bearing.

  The real risks, stated plainly:

  1. Video analysis in 6.5 hours: Full video pipeline is ambitious. The
     practical version: pre-capture 30-60 seconds of footage per task type,
     analyze a fixed set of frames with Claude Vision at build time, store
     extracted steps in MongoDB. During the demo, you play the footage and
     reference the pre-analyzed steps. This is not cheating — the analysis
     pipeline is real, you just run it before the demo clock starts.
  2. What does "the robot doing tasks" look like on screen: This must be decided
     right now. An agentic software system that receives task specs, executes
     tool calls, and returns a measurable score is totally sufficient. You don't
     need physical hardware for this idea to win — the ElevenLabs call IS your
     physical moment.
  3. Harness YAML rewriting complexity: Writing valid Harness Worker Agent YAML
     programmatically is doable but needs one person who has looked at the
     schema before 10:30 AM.

  Verdict: This is better than Sim2Real-Harness. The problem is more universal,
  the narrative is cleaner, the creativity criterion is stronger, and the
  ElevenLabs integration is architecturally justified rather than decorative.
  The only version of this idea that loses is one where "the robot doing tasks"
  is undefined going into the build window. Lock that down first.

⏺ Document 03 is ready at SCRATCHPADS/03-brain-hierarchical-knowledge-graph.md,
  with the plain-text version beside it. A hierarchical knowledge graph is a set
  of nodes where every node except the top one has exactly one parent, and the
  parent covers a broader area than its child. For our robots, the top node is
  the whole warehouse, the next level is zones B, D and M, and the level below
  each zone is TwinForge's four task types. That makes a fixed skeleton of 16
  nodes, which the improver never changes. The four parts of the brain hang off
  those nodes:
  - Rules: behaviours the robot follows, such as waiting at a holding point when
    the lift queue is long.
  - Guardrails: hard limits enforced on every tick, such as a speed cap.
  - Context policies: what memory the robot agent sees when something goes
    wrong.
  - Tool grants: which tools the robot agent is allowed to use.

  A rule attached higher up applies to everything below it, and when two rules
  cover the same behaviour, the one attached lower down wins. A small set of
  human-set limits, which document 03 calls the envelope, overrides everything.

  A robot loads its brain with one MongoDB query that walks up from its task
  node to the warehouse node using $graphLookup, then collects every brain part
  attached along that path. That corrects a small overstatement in document 02,
  which called it a single $graphLookup query. Each brain part also stores
  references to its evidence: the human clip it came from, the failures it
  fixed, and the test result that proved it. Those references let a judge click
  from a rule all the way back to the clip of a teammate waiting beside a
  doorway.

  Brain parts are never edited, only added or retired, each with a version
  number. That makes replaying an old brain, comparing two brains, and removing
  one rule to measure its effect simple filters. Permissions are split by
